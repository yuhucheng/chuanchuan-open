# 全局断开清理失败时的等待边界

全局关闭“允许连接”会先同步撤销 grant 和待处理接入，再异步撤下六码入口、发现广播并关闭现有传输。此前若 `stopAccepting()` 的接入清理报错，`_finishDisconnectAll()` 会直接离开，跳过等待已启动的传输关闭；`stopAccepting()` 自身也会跳过发现撤下和状态通知。

现在两条清理链在同一个断开事务中等待落定；接入清理失败仍向调用方返回失败，已关闭的授权不会因此复活。发现撤下和状态通知放在接入收尾的 `finally` 中。普通失败不应让传输关闭的等待被跳过。

验证：客户端连接/会合/恢复定向 49 项、完整 `flutter test --no-pub` 307 项通过；`flutter analyze --no-pub` 无问题，普通 `lib/main.dart` macOS Debug 构建通过。此次没有人为制造真实服务离会失败或运行双机网络中断；测试证明既有连接行为未回退，故仍保留真实跨网、后台和断网验收待办。

同日退出屏障补充：`shutdown()` 在等待断连、启动和恢复任务时，即使其中一个任务报错，也继续排空这些任务迟到创建的传输关闭 Future，最后向调用者保留原错误。此前该排空只位于成功分支，失败可能让进程清理过早结束。连接控制器定向 16 项、客户端完整 307 项及静态分析通过；没有故意制造平台级离会错误或据此宣称后台实机验收完成。
