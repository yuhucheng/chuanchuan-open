本清单用于**产品入口 + 真实双击 + 真实手势**的现场验收，覆盖 `plan-desktop-platform-completion` 的 6.1（生命周期与记录）、7.1（托盘/菜单栏入口与关闭到后台）、7.2（隐藏仍持续采集、退出释放、来源失效不回退），并顺带留取 3.1 / 6.2 的产品构建与版本记录。

此前这些项目的 macOS 证据全部来自开发入口 `lib/dev/macos_acceptance_main.dart`，手势由程序化等价手段触发。本清单补的正是**产品入口**与**真实手势**这两条线。

## 环境

- macOS 26.6.2、Flutter 3.47.2、客户端 `0.1.0-dev.1+1`、媒体 SDK `0.1.0-dev.1`、媒体 API `0.2.0`。
- 构建：`flutter build macos --debug --no-pub`（Debug，经 `AppInfo.xcconfig` 套用本机证书 `Chuan Local Development`）。

## 观测手段与边界

### 可观测（不需要任何 TCC 授权）

| 通道 | 内容 |
|---|---|
| `CGWindowListCopyWindowInfo` | 应用自有窗口的数量、层级、坐标、是否在屏；窗口**标题**被系统屏蔽 |
| `NSRunningApplication` | 进程存活 / 隐藏 / 前台 / 终止 |
| `proc_pidinfo(PROC_PIDTASKINFO)` | 进程累计 CPU 时间（据此算占用率）与线程数 |
| `CGGetActiveDisplayList` | 显示器集合与主屏标识 |
| 文件系统 | 崩溃报告计数、应用容器状态 |
| Window Server 窗口清单 | 逐样本聚合，用于比对采集期间是否出现新的系统窗口 |

采集工具：`tool/observe_desktop.swift`（只读，每 2 秒一个 JSON 样本，输出 JSONL）。

```sh
xcrun swiftc -O -o /tmp/observe_desktop tool/observe_desktop.swift
/tmp/observe_desktop --match "Share Hub" --interval 2 --duration 1800 --out /tmp/field.jsonl
```

### 不可观测（本项目已知限制，不得由可观测项替代）

| 通道 | 原因 |
|---|---|
| 截图 / 录屏 | 本进程无屏幕录制授权 |
| UI 自动化与真实点击模拟 | 无辅助功能权限 |
| 系统统一日志 `log show` | 拒绝在沙箱内运行（`log: Cannot run while sandboxed`） |
| **菜单栏项是否存在** | 实测 macOS 26 上状态栏项由系统宿主渲染，**不以应用自有窗口形式出现**（应用正常运行时高层级窗口数为 0），故不能用窗口枚举证明或否证 |
| 预览画面内容 | 无截屏授权 |

因此本清单把证据分成两类并分开标注：**客观信号**（我采集）与**界面事实**（你确认）。二者都不足以单独构成某项验收结论时，如实记录为未支持条件。

### 对端身份（Bonjour 反查）

`dns-sd -B` / `-L` 解析出两个本产品实例：本机 `appledeMacBook-Pro-2.local.:65237`（TXT `name=我的 Mac platform=macos`，实例 ID 与容器 `discoveryID` 一致）；对端 `MAXHUB-LXXY.local.:1096`（TXT `name=我的 Windows platform=windows`），而 `MAXHUB-LXXY.local` 解析为 **172.20.102.24**，即上面那条连接的对方。

对端当前广播的 SRV 端口是 1096，与我们所持连接的 18956 不同；双方 TXT 目前都只有 `v/id/name/platform`（端点 `host/port/key` 只在真正开放接入时写入），即**此刻双方都没有开放可连接的入口**。

### 代码事实（解释「没有可执行的操作」）

- `TrustedConnection.capabilities => const {}`（`packages/share_hub_connection/lib/src/session.dart:182`，注释原文 *No remote media/input/file implementation has been accepted yet*）。**能力集恒为空集**，任何平台、任何对端都协商不出能力，所以「暂无可用操作」是本阶段的既定行为，不是对端的问题。
- 由此，弹窗文案「对端未协商任何操作能力」把原因归给了对端，与实际不符（准确说法是「本版本尚未交付远程操作契约」）。**文案准确性问题，未改。**
- `ConnectionController.message` 是**单一粘性字段**：失败时覆写为「连接未建立…」，成功时覆写为「身份验证通过…」。所以顶部横幅与弹窗并不矛盾——横幅反映**最近一次连接尝试**的结果；但两者同屏会被读成「状态自相矛盾」。**呈现问题，未改。**

### 尚未确定

Windows 平台在本仓**没有连接实现**：`windows/` 下不存在任何 `connection.*` 通道方法，托盘项在 Windows 上是「允许连接（当前平台不可用）」且置灰，其 presence 监听器与 macOS 同构（accept 后立即 `closesocket`，仅宣告存在）。连接能力（提交 `f05e53b`）只改过 `macos/` 与 Dart，**未触及 `windows/`**。

因此这次配对**是如何建立起来的仍未确定**：需要回忆 6 位短接码当时显示在哪台机器、在哪台机器上输入，以及那台 Windows 机上的 app 是否确实由本仓构建。在此之前不对这条连接的来源下结论。

**B. 采集活动：本窗口内未发生**

- 累计 CPU 0.182s → 0.481s，1 小时净增 **0.299s**；瞬时占用率均值 **0.0086%**、峰值 **0.35%**（15:52:57）。**无任何采集级占用**（采集应有 CPU 明显抬升 + 线程跃升，二者均未出现）。
- 前台按样本数：ToDesk 683 > ChatGPT 551 > WorkBuddy 224 > Chrome 60 ≈ Code 60 > 飞书 40 > **Share Hub 10**。Share Hub 仅在 15:52:55、15:57:04–10、16:21:48、16:23:20–22 等零星时刻短暂到前台，CPU 峰值也落在这些时刻（0.2%–0.35%），是窗口切换带来的瞬时开销，不是采集。
- 结论：**与上一窗口一致，本窗口内用户未做任何采集操作**（P3–P10 的采集/最小化/隐藏/关闭到后台序列仍未执行）。

**C. 录屏指示（`StatusIndicator`）与采集无关的交叉证据**

- `StatusIndicator` 条目（按名字匹配，非 `<redacted>`）在窗口内**可观测**：`onscreen` 恒为 **4**（1631/1631 零变化），`offscreen` 于 15:52:51 从 0 → 2 后保持。
- 但该信号**不能归因于 Share Hub**：① 它从窗口第一秒到最后恒定，而 Share Hub 的 CPU/线程/窗口全程没有任何采集特征；② 本机前台 top1 是 **ToDesk**（远程桌面，本身常驻屏幕共享），`Snipaste` 也在运行——`StatusIndicator` 是**系统级录屏/屏幕共享指示**，任何采集方都会触发。因此「onscreen=4」几乎必然来自 ToDesk 等第三方，而非本产品。
- **口径重申**：上一轮已确认「窗口名对无授权进程是屏蔽的，空闲基线按名字匹配 `StatusIndicator` 得 0 既不能证明有也不能证明无」。本窗口因为 ToDesk 常驻共享，名字 `StatusIndicator` 反而被观测器拿到非零计数，进一步证明**不能用这个计数单独判读本产品的录屏状态**——要判读只能做「本产品采集态 vs 空闲态」的**同源差异**，且必须叠加 CPU/线程的联动信号。本窗口没有任何这样的联动，故不构成 7.2「隐藏仍持续采集」的证据。
