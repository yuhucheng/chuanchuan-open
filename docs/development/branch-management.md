# 版本、分支与提交规则

本规则同时适用于 `chuanchuan` 闭源 SDK/服务仓库和 `chuanchuan-open` 开源客户端仓库。当前目标版本见根目录 `VERSION` 和 [版本计划](../version-plan.md)。版本计划是提交归属依据，不能为了某次任务临时发明版本或分支。

## 分支

- 日常开发统一使用既有 `main`。Windows、macOS、Android 和助手任务不单独建分支；开始工作先检查当前分支，不执行自动建分支或自动 worktree 流程。
- 在 `main` 上完成小而完整的提交，先验证再推送。已有其他分支上的工作先检查远程差异，再合并到 `main`，不得直接重置或丢弃。
- 只有项目负责人明确批准例外，并在版本计划中记录目标版本、用途、负责人、起点及回合条件后，才可创建分支。候选命名为 `release/vX.Y.Z` 或 `hotfix/vX.Y.Z`；名称并不自动构成授权。启用例外时还须同步调整检查规则，不能用 `--no-verify` 绕过。
- 当前没有获批的例外分支。历史 `feat/*`、`codex/*` 分支在合并后只作历史参照，停止追加提交；未经明确要求不删除远端历史分支。
- 不 force-push 共享历史，不在推送后随意改写提交。远程有更新时先 fetch、核对差异，存在冲突则正常解决并复验。

## 版本与提交

提交前确认改动属于当前版本计划；新增范围先更新计划。`VERSION` 记录目标稳定版本，例如 `0.1.0`；开发包可使用 `0.1.0-dev.N`，客户端还可附加构建号。公共 API 版本独立维护，兼容性必须另行验证，不能机械跟随产品版本升级。

新提交标题格式：`类型(v目标版本): 具体改动`。允许 `feat`、`fix`、`refactor`、`docs`、`test`、`build`、`ci`、`chore`、`merge`。例如：

```text
fix(v0.1.0): retain the preview engine across parent rebuilds
merge(v0.1.0): integrate macOS preview into the required SDK architecture
```

一次提交应是可以解释和验证的完整变更，不混入其他版本的功能。合并历史提交不追溯改写旧标题，但本次新建的合并提交必须符合格式。变更较多时，提交正文说明改动、验证结果和尚未验收的部分。

## 两个仓库的协作

1. 两端开始工作先 fetch，查看 `status`、当前分支和远端差异，阅读版本计划。
2. 接口、客户端与 SDK 的协同修改在本地一起验证，接口保持兼容；不把私有实现复制到开源仓库。
3. 先提交并推送开源仓库，再将闭源 `open-source.lock.json` 更新到已验证的开源提交；最后提交并推送闭源仓库。
4. 记录两端提交关联。构建/测试没有覆盖的平台明确标注待验收，不能将 Mac 历史布局的测试结果当作新 SDK 布局的编译证明。
5. 推送后 fetch 并确认本地 `HEAD` 与 `origin/main` 一致。发布标签仅在版本验收完成并确认发布时创建；开发提交不意味着正式发布。

## 本地检查

每个新克隆的仓库运行 `pwsh -File tool/install_git_hooks.ps1`。仓库内 `.githooks` 会在提交前检查当前分支为 `main`，读取暂存区的 `VERSION`，并检查提交标题。可运行 `pwsh -File tool/test_git_policy.ps1` 验证检查行为。

这些检查只在安装后的本地仓库生效，不等同于 GitHub 服务端保护，也不能验证负责人是否真的批准了范围。开发者和助手仍须遵守本规则；不要禁用钩子或绕过检查。已有自定义钩子时安装脚本会保留原配置，需先合并其行为。
