# plan-sdk-distribution 设计摘要

## Context

pubspec 直接依赖标准 SDK 目录，配置脚本建立链接且不复制源码。目前贡献者说明仍使用内部开发适配包，正式二进制 SDK 尚未产出。动机见 proposal.md。

本文件是既有设计迁移，lifecycle/delivery 均为 planned，能力尚未实现；此次只整理规格，不表示已授权实施，也不恢复已停止的产品开发。规格版本 0.1.0、产品基线 0.1.0、release-target 0.1.0。具体实现需另行进入 apply，并先解决下文的设计门槛。

### 已确认的公开产品约束

用户已确认正常客户端与贡献者构建统一要求 SDK；闭源 SDK 按统一条款免费集成和分发，允许商业产品集成，终端使用资格与分发权分别处理。自有开源客户端采用 Apache 2.0，上游许可各自保留。

## Goals / Non-Goals

让公开客户端在无 SDK 实现源码访问的环境消费可验证制品，并明确包版本、公共 API 范围和平台能力。非目标：此次不选择签名供应商、不编造制品地址、不交付 ABI 或授权文本。

## Decisions

以下划分保留用户已确定的边界；标为候选的内容仍是未实现的技术建议，不提升为已确认产品需求。

1. 保留标准目录与唯一入口。正式包可按相同布局安装，开发链接则清楚标记内部适配；另外创建无 SDK 产品入口会违背已确认构建要求，因此不采用。

2. 候选发布清单包含制品版本、架构、契约范围、能力、完整性校验、许可和依赖通知。具体元数据格式须与 SDK 发布方共同设计，不能由客户端单方面发明已发布协议。

3. 版本分别维护：产品版本、规格版本和公共 API 版本不是同一计数器。兼容检查按 API 和平台能力确定；仅字符串版本相等不足以证明原生可加载。

4. 发行验收分别检查可构建、插件/依赖可加载、实际功能和可信签名。免费 SDK 集成不等于终端免激活，也不把闭源附加条款施加到 Apache 2.0 客户端模块。

## Risks / Trade-offs

- 源码路径被误称为二进制 → 文档保留开发阶段标识，正式包另附证据。
- 错误架构或传递依赖缺失 → 干净环境验证安装、加载和功能。
- 不完整签名检查掩盖加载失败 → 验收实际 EXE/应用及依赖加载，渠道选择另定。

## Migration Plan

先明确 API/制品兼容清单和授权交付，再扩展安装诊断，用匹配正式包构建公开客户端。安装失败保留旧包；契约不兼容时明确失败并指导使用兼容包。正式发行后再更新已验收平台与制品链接。

## Decisions Required Before Implementation

ABI、包容器、签名渠道、下载服务、SDK 许可证定稿和稳定发行平台清单必须在发布前完成；是否需要自动更新由后续需求决定，本次不增加。

当前计划文件已整理齐全，但这些门槛解决前不应声称具备可直接执行的最终接口设计。任何新增产品范围先更新版本计划，具体任务见 tasks.md，全部保持未完成。
