# 正式 SDK 消费与兼容

## Purpose

将既有设计中的正式 SDK 消费与兼容整理为可审阅的未来行为契约。当前能力尚未实现，本次仅迁移规格；规格版本独立维护，目标版本只说明规划归属，不代表已经授权开发、完成验收或承诺发布日期。

## ADDED Requirements

### Requirement: 贡献者可取得的必需 SDK

正式客户端构建 MUST 始终接入 SDK，并提供贡献者可按统一免费集成分发条款取得的 SDK 包；闭源只限制实现源码公开，不得被描述为贡献者无需 SDK 或无法取得 SDK。

#### Scenario: 新的贡献者构建

- **WHEN** 贡献者没有 SDK 实现源码但取得正式匹配包
- **THEN** 可按公开安装说明使用标准包布局构建同一产品入口。

### Requirement: 版本和能力兼容

SDK 制品 MUST 声明 SDK 版本、兼容公共 API 范围、支持平台与架构及实际能力；客户端发现不兼容时明确拒绝启用对应能力，不以修改 UI 状态绕过检查。

#### Scenario: API 不匹配

- **WHEN** SDK 声明的契约范围不包含客户端公共 API 版本
- **THEN** 报告契约不兼容和可行动的安装提示，不宣称媒体实现已经可用。

### Requirement: 制品来源与失败区分

接入说明和工具 MUST 区分缺少 SDK、包布局错误、制品校验失败、平台不支持和契约不兼容；安装取消或失败不得覆盖用户已有的有效包。

#### Scenario: 校验失败

- **WHEN** 下载或复制后的 SDK 制品未通过发布方提供的完整性检查
- **THEN** 停止安装并保留原包，不运行该制品。

### Requirement: 真实发行说明

正式 SDK 消费文档 MUST 同时提供对应许可、第三方通知、制品身份和已验收平台记录；内部源码适配器、测试构建和可信发行签名分别标明。

#### Scenario: 只有内部适配器

- **WHEN** 发布说明尚无正式二进制和签名验收
- **THEN** 明确未交付，不虚构下载地址或称其为已发布 SDK。

## Verification

- 在无 SDK 实现源码访问的干净环境，用正式包验证公开客户端标准入口、平台插件和发行依赖。
- 注入缺包、错误布局、校验不匹配及 API 版本不匹配，确认诊断与保留旧包行为。
- 当前正式二进制包、ABI 和可信发行签名仍待交付；开发适配器不能通过该验收。

所有场景均为待验收项；现有单元测试、局部平台构建与媒体实验不构成本能力已经交付的证据。
