# plan-remote-screen-sharing 设计摘要

## Context

当前 PreviewEngine 仅描述本机 sources/start/stop/view 及两个回调。公开控制器具备选择与清理编排，但 Windows 首帧和 macOS 当前插件仍有实机缺口。动机见 proposal.md。

本文件是既有设计迁移，lifecycle/delivery 均为 planned，能力尚未实现；此次只整理规格，不表示已授权实施，也不恢复已停止的产品开发。规格版本 0.1.0、产品基线 0.1.0、release-target 0.1.0。具体实现需另行进入 apply，并先解决下文的设计门槛。

### 已确认的公开产品约束

用户已确认屏幕共享包含发送与观看；它与输入控制分别描述和授权。音频、多显示器和一对多仍未确认。

## Goals / Non-Goals

先定义可被两端验证的远端状态、来源和会话终止契约，再接入具体 SDK。非目标：本次不实现或恢复远端会话，不把本地预览测试升级为跨设备验收。

## Decisions

以下划分保留用户已确定的边界；标为候选的内容仍是未实现的技术建议，不提升为已确认产品需求。

1. 保持本地预览契约稳定；规划新增版本化远端会话描述，包括对端身份、发送/观看能力、状态、失败与幂等清理。直接复用本地 firstFrame 回调会混淆发送端与接收端证据，故需要明确远端状态来源。

2. 观看请求与来源选择先于采集启动；来源失效必须由用户重新选择。使用整个显示器作为自动回退会改变用户实际分享范围，因此不采用。

3. 连接与媒体分开诊断：会话网络建立不等于解码和呈现成功。SDK 负责媒体执行，公开客户端负责状态、来源选择和用户停止；双方共同验证身份和必要授权。

4. 候选验收使用可辨识的独立测试窗口，在接收端确认内容与来源；编码、帧率、时延目标待平台实验后确定，不硬编码成既有承诺。

## Risks / Trade-offs

- 本地有帧而对端黑屏 → 独立对端首帧和超时状态。
- 旧回调污染重连 → 用会话身份与尝试代次限定事件，取消后清理晚到资源。
- SDK 状态与 UI 不一致 → 契约要求明确错误和清理完成，实机检查停止后的帧更新。

## Migration Plan

实现前先完成可信连接和公共远端契约评审，保留旧本地 PreviewEngine 接口兼容。随后分别集成发送/观看，进行权限与来源失效检查，再进行双机直连/中继验收。不兼容的媒体协议明确拒绝；不静默降为没有授权的路径。

## Decisions Required Before Implementation

远端契约具体类型、能力版本、来源几何、媒体状态确认机制必须先设计；音频、多屏、一对多和性能指标需进一步产品决定。macOS 当前插件和 Windows 首帧缺口也须有对应真实验证。

当前计划文件已整理齐全，但这些门槛解决前不应声称具备可直接执行的最终接口设计。任何新增产品范围先更新版本计划，具体任务见 tasks.md，全部保持未完成。
